# Client invoicing module

Accepted immutable sales order -> draft billing details -> issued sequential invoice -> manual payment evidence -> immutable reversal/full credit -> replacement invoice. Only company owners/admins access these APIs and document downloads. This is an operational ledger, not a payment gateway, automatic bank reconciliation or certified accounting/tax package.

Amounts and currencies copy the accepted order; draft edits cannot change items, totals, terms or customer identity. Issuing locks billing details and assigns INV-000001 within the company. Separate CREDIT counters assign CN-000001. Counter updates are transactional and roll back with failed issuance. PostgreSQL source creation uses a scoped advisory transaction lock because append-only sales orders intentionally lack UPDATE permission; it never broadens their grants. Unique source generation/parent links make initial/replacement creation safe on retries.

Every ledger writer locks its invoice, validates its current version and bumps that version. Read details take a shared lock to avoid mixing payment and credit snapshots across concurrent commits. List amounts use one SQL snapshot and sum only active positive payment allocations, avoiding signed-history overflow in SQLite after many reversals. Canonical minor-unit strings/BigInt retain exact values up to9007199254740991; currencies are never mixed into a single aggregate.

Payment creation uses an original-payload request hash/key and unique invoice receipt reference; it rejects wrong currency, future dates and overpayment. A reversal appends one full correction linked to the original record and moves no money. Full credit is permitted only with zero active payments and preserves original subtotal/tax/total. It does not process a refund. Fully credited invoices can have one replacement child with a new number; old invoice and credit remain unchanged. Partial credits, real refunds, payment processing, rate/time billing and edits to accepted order prices are deferred.

Migration008 adds five forced-RLS tables. Runtime invoice/counter rows SELECT/INSERT/UPDATE; item/payment/credit history SELECT/INSERT only. Database triggers freeze snapshots/issued headers and existing history rows. Trigger functions are invoker functions with fixed search_path; PUBLIC execute revoked and restricted-role execution explicitly granted. API membership/role checks remain necessary for the private shared credential. No DELETE, arbitrary numbering or ledger rewrite API.

PDFKit0.20.2 (MIT, https://github.com/foliojs/pdfkit) is pinned in package/lock files; installed with scripts disabled. Server exports in-memory issued snapshots without browser, filesystem or external-service dependencies. Initial built-in font export supports printable basic Latin text plus line breaks/tabs; unsupported text returns422 rather than silently dropping characters. Full Unicode records remain readable online. PDFs carry the original invoice amount, not a changing payment statement. Text flows over pages; each item stays with its quantities/amounts. Actual invoice/credit and seven-page-or-longer document exports are rendered/extracted and checked before acceptance.

See docs/erp/INVOICING_SPEC.md and INVOICING_ACCEPTANCE.md. Deployment, external invoicing messages, customer identity verification, paid calls and commercial launch remain separate gates.
