# Approved time to client invoice — implementation contract

Status: implementation contract. Rate foundation and local TIME invoice flow now exist; actual scoped evidence and remaining gates are in TIME_INVOICES_ACCEPTANCE.md. This specification alone is not acceptance. Full ERP and commercial gates remain open; the original human-testing database and port 3039 are outside this work.

## Existing behavior inspected

Sources: `backend/src/modules/timesheets/{schema,service,routes}.js`, `backend/src/modules/invoicing/{schema,service,routes,pdf}.js`, `app/client/src/{TimesheetWorkspace,InvoiceWorkspace}.jsx` and master-plan module scope.

Time entries have whole minutes (1–1440), UTC work date, project/task, worker, billable flag, version and immutable approval history. Only a different authorized reviewer may approve submitted time. APPROVED entries currently have no outgoing state transition and no billing allocation. Invoice creation accepts only `salesOrderId`; snapshots immutable order items. `sales_order_id` is NOT NULL, generation uniqueness is order-based, and replacement creation reloads its order. Invoice items currently display integer quantity multiplied by unit minor amount. Financial amounts use canonical minor-unit strings and BigInt; totals are bounded by 9007199254740991. Owner/admin controls finance; time review additionally permits the appropriate manager. These permissions must remain distinct.

## Rate foundation

Owner/admin sets an explicit project hourly rate and supported currency; no inferred wage, default price, exchange conversion or tax. A saved rate has a version and audit evidence. Updating a rate requires its current version. A rate is a pricing setting, not approval of time. Finance-only rates must not leak through ordinary worker/project/time reads. UI says “Hourly billing rate”, shows currency and actual amount, includes loading/error/retry, and preserves unsaved edits on version conflict.

Snapshot rate ID/version, hourly minor amount and currency into a billing allocation when the invoice draft is created. Later rate edits never change the allocation or draft/issued totals. If the creation request was retried after a rate change, return the original committed snapshot for the same request; changed request input yields 409. Reject missing/inactive rates and mixed currencies explicitly. Initial rate selection is the current explicitly selected project rate, not a silently backdated effective-rate system.

## Distinct invoice sources and immutable allocation

Introduce explicit source `ORDER` or `TIME`; preserve all existing order invoices as ORDER. ORDER requires a sales order and retains existing generation/idempotency behavior. TIME requires its own immutable billing batch/root reference and must have no sales-order ID. Do not fabricate orders to fit existing schema. Add CHECK constraints expressing mutually exclusive sources, tenant-composite foreign keys, appropriate unique indexes, forced RLS and restricted grants.

Use an immutable allocation table linking company, billing root, time-entry ID, approved entry version/submission, approving decision ID, project, customer snapshot/reference, rate snapshot, integer minutes, currency and computed amount. A company/time-entry unique constraint reserves each entry once across all original drafts, issued invoices and replacement generations. Initially bill whole approved entries only; partial minute allocation requires a separately designed remaining-minute invariant. An allocation's root can link multiple invoice generations, but never create a second billable claim for the same time. Allocation update/delete is forbidden in SQLite and restricted PostgreSQL runtime. No silent draft deletion/release path.

Eligible entries are APPROVED, billable, in the selected company/project, associated with the selected customer through a valid same-company project/customer relationship, and not already allocated. Recheck eligibility inside the write transaction; list results alone do not authorize billing. Lock selected time records in deterministic ID order, validate customer/rate/approval, then atomically save root, allocation, draft invoice/items and audit. Unique constraints must make simultaneous overlapping requests yield one allocation, with a legible 409 for the loser. A forced audit failure must roll back the entire allocation and invoice. Bound selected entry count (for example 100) and paginate eligibility search; never select all hidden pages implicitly.

Creation request contract: `POST /api/v1/client-invoices/from-time` with `{requestId, projectId, customerId, rateVersion, entryIds}`. IDs are unique, count bounded; input rejects unsupported fields. Return `{invoice,replayed}` using the existing detail shape plus explicit source, billing root and time-line provenance. Preserve the existing ORDER POST unchanged for compatibility. Scope retry uniqueness by organization and billing request, canonicalize the sorted entry IDs for the fingerprint, and validate current role before returning replays. Never accept client-computed money or worker approval claims.

## Exact money and document rendering

For each entry: `lineMinor = (BigInt(minutes) * BigInt(hourlyMinor) + 30n) / 60n` for nonnegative values: integer division, half up once per entry. Sum rounded lines; never round aggregated minutes and redistribute. Examples: 1 minute at 30 minor/hour = 1 minor; 1 at 29 = 0; two separate 1-minute entries at 30 total 2 minor. 90 minutes at 10001 = 15002 minor. Validate each line and summed total against the existing money limit before writes. A zero rounded line remains visible with exact minutes; do not inflate it to a minimum charge. Keep minute and amount representations exact in responses/charts/exports.

TIME lines must explicitly show work date, description, minutes and hourly rate, rather than misusing integer `quantity` to imply decimal hours. Extend line source metadata or a dedicated time-line table; existing ORDER quantity/unit/tax display and historical PDFs remain correct. TIME tax is zero with “No tax configured”, not a claim of exemption or legal compliance. Do not infer tax from customer country or copy unrelated order tax. Nonzero tax, discounts and cross-currency pricing need separate approved contracts. PDF and report/export paths must include accurate source/minutes/rate/amount; retain the existing explicit unsupported-text error rather than losing text.

## Credit and replacement

Retain existing full-credit, no-active-payments restriction and immutable original documents. Full credit does NOT release allocated time for rebilling. TIME replacement copies the original allocation and immutable amount snapshots within the same root, links `supersedes_invoice_id`, increments generation and receives a new invoice number when issued. It must not reload current rates or call the order-only insert path. Retry returns the existing child. Concurrent replacement cannot fork generations. This initial correction flow changes billing details only, matching current invoice behavior; changing billed minutes/rates requires a separately specified adjustment workflow.

## Compact workflow

Owner/admin: Invoices → New invoice → choose Sales order or Approved time. Approved time requires customer/project, shows current saved rate/version and exact currency, then paged eligible rows with date/worker/task/description/minutes and calculated line amounts. Selection summary shows selected count, minutes and exact sum; never call this “hours approved for payment”. Confirm creates a draft, then opens existing invoice review/issue/payment/correction flow. Missing rates offer a clear route to project billing settings. Reassignment, expired session, read-only subscription, stale rate, already allocated work and no eligible time have distinct messages; preserve selection where safe and refresh after conflict. Company switch cancels pending requests and resets rate/selection/customer. Mobile uses readable rows and persistent labels; keyboard selection, focus on completion, and no horizontal document overflow are acceptance requirements.

## Migration and proof gate

Do not edit checksummed historical migrations. A forward migration must handle SQLite table rebuild constraints and PostgreSQL NOT NULL removal, replacement of source/generation uniqueness, source-aware immutable guards and RLS/grants. Preserve all prior foreign keys, indexes, triggers and populated rows. Explicitly update runtime required-table inventory, money normalization, report joins, PDF/UI source branches and test fixture schemas; avoid INNER JOIN sales_orders that would hide TIME invoices. Verify populated prior-version upgrades under actual restricted roles and genuine DB backup/restore with both source types.

Meaningful acceptance: worker logs 90 minutes; different reviewer approves; owner configures rate 10001; draft is exactly 15002 minor and linked once; issue/PDF/payment/full-credit/replacement preserve exact provenance and prevent rebill. Include rejected/submitted/nonbillable/unassigned/foreign-company entries, missing/mixed rates, unauthorized finance reads, subscription lock, rate conflict, retry input mismatch, concurrent overlapping selections, audit rollback, rounding boundaries/overflow, rate edits after draft, replaced/credited entries remaining unavailable, source-specific order regression, restricted raw mutation denial, populated upgrade and recovery. Run real browser selection→draft→issue at desktop/mobile, not only build/unit checks. Report actual command exits and fixture evidence; no hosted or legal readiness claim.
