# SaaS subscription foundation — 20 October 2026

Base `fc0f0a7`, branch `codex/erp-foundation`. This is a locally verified subscription/access foundation, separate from ERP client invoicing. It is not a paid rollout, merchant integration acceptance or a completed commercial billing module.

## Implemented vertical flow

With explicit billing configuration enabled: create a company → persisted trial → provision a trusted owner/provider binding → receive a raw-body authenticated subscription snapshot → reconcile ordering/deduplication locally → enforce company access, seats, AI allowance and configured module features → show access/history in the browser. Existing development behavior remains available for unenrolled companies when billing is disabled. An already enrolled company becomes read-only when an explicitly initialized process is missing its policy; a worker cannot silently treat that paid/enrolled company as unmetered development data.

Migration `011_subscriptions` adds company-scoped subscriptions and minimal event receipts. Both tables FORCE PostgreSQL RLS; provider subscription IDs and event IDs have uniqueness constraints. Runtime grants permit subscription SELECT/INSERT/UPDATE and event SELECT/INSERT only. No event rewrite/delete grant, schema ownership, BYPASSRLS or public table permission is introduced. Prior migration 002–010 SQL/checksums remain unchanged. Existing companies are not silently assigned a new trial by the migration. With enforcement enabled, an unenrolled existing company is read-only until an operator provisions its subscription.

### Access and entitlements

- Explicit JSON policy defines initial plan, trial/grace days, seat cap, daily AI attempt allowance and module inclusions. Configuration validates plan/price mappings, rejects prototype/unknown plan references, and cannot be silently changed on a live database adapter. Restart with a reviewed policy to change configuration.
- TRIAL/ACTIVE require a future recorded access period. Past-due grace begins at the first accepted transition to PAST_DUE; later updates do not extend it. At expiry, cancellation, pause, missing enrollment or reconciliation conflict, ordinary company writes are blocked with 402. No company data is deleted. Reads and otherwise permitted exports remain available.
- The service transaction layer checks the existing parameterized module mutation paths, not only UI buttons. Billing-enabled non-snapshot PostgreSQL transactions serialize per company before domain row locks; the subscription decision is cached for that transaction. Other companies remain independent. Snapshot reports keep their repeatable-read behavior. This is an explicit V1 consistency tradeoff; production contention/load targets remain unverified.
- Invitation acceptance counts current memberships atomically, including across processes. Downgrading below current usage does not delete members; new seats are blocked. A provider subscription binds to only one company. This does not implement verified-signup/trial-abuse controls or a company-creation quota.
- AI processing checks both ordinary operational quota and the configured plan allowance. Workers use the same checks. Already authorized extraction may finish storing REVIEW/FAILED after access changes; it cannot create business records. Authorized discard/content cleanup remain possible while read-only. Mandatory human/independent approval safeguards are never bypassed to fit a package.
- Retained resource reads remain available; configured summary-report access and mutations respect feature flags. Full entitlement-aware presentation across every form, Starter's proposed “limited” timesheet policy, monthly usage/token/cost accounting, all-company export windows and eventual retention/deletion policy remain unfinished.

### Authenticated provider events

`POST /api/billing/paddle-webhook` is intentionally outside session authentication and the `/api/v1` trusted-Origin requirement and before JSON body parsing. It accepts the bounded raw JSON body and verifies `Paddle-Signature` using the notification destination secret, `ts:rawBody` HMAC-SHA256, constant-time comparison and a five-second timestamp tolerance. Multiple `h1` values are supported. No event parsing/business effect occurs before verification. This follows [Paddle signature documentation](https://developer.paddle.com/webhooks/about/signature-verification/).

Only supported subscription lifecycle snapshots are normalized. A single mapped price/quantity is supported; unmapped/add-on configurations fail closed for access and require reconciliation. A future scheduled cancellation/pause bounds the effective period; an already canceled/paused status is read-only immediately.

The signed organization hint is only a selector: the existing server-provisioned company/customer/subscription pair must match before processing. There is no customer HTTP route to bind arbitrary IDs, edit status or self-upgrade. `createBillingService().bind()` is a trusted server/operator integration primitive, requires the company owner, and does not grant a paid status. Production ownership verification/provisioning workflow is not implemented yet.

Event IDs deduplicate normalized content; conflicting reuse is rejected. Older `occurred_at` snapshots are recorded but ignored. Equal timestamps with equal access state are ignored; conflicting equal timestamps set a reconciliation flag and block writes. A newer full snapshot may recover access. Minimal event identity/hash/type/timestamps/outcome are retained, not raw provider payload, card data or secrets. This applies [Paddle's event ID/order guidance](https://developer.paddle.com/webhooks/about/how-webhooks-work/) and its [subscription provisioning guidance](https://developer.paddle.com/build/subscriptions/provision-access-webhooks/). Periodic provider-API reconciliation, manual resolution controls and real callback delivery remain launch work.

## Configuration and preview boundaries

`BILLING_ENABLED=0` is the default. Opt-in requires `BILLING_POLICY_FILE`; the webhook additionally requires `PADDLE_NOTIFICATION_WEBHOOK_SECRET` (destination secret, not API key). The API and dedicated worker both initialize billing configuration. A test-only policy is refused in production mode.

`backend/test/fixtures/subscription-policy.json` is expressly a **test policy**: proposed package names/seats 3/10/25, fixture AI allowances 1/3/10, a 14-day trial and a 3-day grace exercise behavior. Its synthetic Paddle price IDs are not merchant products or finalized prices. No commercial prices or retention promises were invented. These values must not be presented as approved packages.

`node scripts/start-subscription-verification.mjs` serves **http://127.0.0.1:3027** against fictional local SQLite data, with no checkout/payment method and AI provider calls disabled. Every billing screen identifies the provisional policy. Browser acceptance signs synthetic events locally and invokes the trusted fixture binding helper; it does not connect to Paddle, create a merchant account, charge/refund money or prove receipt of a real provider event.

The admin UI shows current state/access, configured plan/limits, inclusions and minimal event history. It distinguishes the recorded period end from current effective access. Company context is checked before displaying subscription metadata; member users cannot read admin event history. Refresh updates the global read-only banner and disables parent project/invitation controls. Other module forms still rely on authoritative server denial and normal error recovery; not all controls are proactively disabled yet.
